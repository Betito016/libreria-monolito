Módulo SOAP para Clasificar el Catálogo de una Librería

Diseño, construcción, pruebas y documentación técnica de un servicio SOAP 1.1 desacoplado en Flask + psycopg2 con WS-Security, manejo de SOAP Faults y persistencia PostgreSQL.

01

Objetivo y Scope del Ejercicio

Objetivo Principal: Diseñar, implementar y validar un módulo de servicios web SOAP 1.1 en Python (Flask + psycopg2) que permita a aplicaciones de escritorio clasificar conceptos tecnológicos en modelos de nube (IaaS, PaaS, SaaS, FaaS) integrándose con la base de datos PostgreSQL de un monolito Node.js preexistente, sin modificar el código fuente ni alterar las tablas del monolito.

03

Descripción del Monolito y del Módulo SOAP

El Monolito Node.js: Aplicación existente encargada de la gestión de catálogo de la librería (libros, precios, stock, autores y usuarios clientes). Posee un modelo de datos consolidado en PostgreSQL que no debe ser alterado para garantizar la estabilidad operativa del negocio.

El Módulo SOAP: Servicio especializado en ingeniería de datos y clasificación colaborativa Cloud (IaaS, PaaS, SaaS, FaaS). Publica un contrato WSDL estricto y opera como subsistema autónomo que desacopla a los clientes de escritorio de la estructura interna de la base de datos.

04

Diseño de Datos y Tablas Propias del Módulo

Para no contaminar ni modificar el esquema del monolito, se implementaron 3 tablas independientes, vistas y restricciones estrictas:

Tabla Columnas Principales Restricciones y Llaves Propósito / Justificación
clasificadores id, nombre, apellidos, email, creado_en PK: id
UNIQUE: email		 Aislar la identidad del usuario clasificador sin reutilizar la tabla users del monolito.
clasificaciones_cloud id, concepto_id, libro_isbn, clasificador_id, modelo_cloud, fecha_clasificacion, ip_origen, cliente_tipo, cliente_id PK: id
FK: concepto_id -> concepts
FK: libro_isbn -> books
FK: clasificador_id -> clasificadores
CHECK: modelo_cloud IN ('IaaS','PaaS','SaaS','FaaS')
UNIQUE(clasificador_id, concepto_id)		 Registro transaccional de clasificaciones con auditoría técnica y prevención absoluta de clasificaciones duplicadas por el mismo usuario.
clientes_servidos id, tipo_cliente, identificador_cliente, peticiones_atendidas, ultima_peticion PK: id
UNIQUE: identificador_cliente		 Métricas de telemetría y auditoría de clientes SOAP que consumen el servicio.
🔒 Política de Mínimo Privilegio en PostgreSQL: Se define el rol soap_app_user que tiene únicamente GRANT SELECT sobre las tablas del monolito (books, concepts, book_concepts, categories) y GRANT SELECT, INSERT, UPDATE sobre las tablas propias (clasificadores, clasificaciones_cloud, clientes_servidos), eliminando riesgos de alteración involuntaria.

Contrato WSDL y Tipos XSD (Auditoría)

El contrato formal se encuentra publicado en el endpoint /soap?wsdl bajo el target namespace http://udem.edu/iac/library/soap.

Matriz de Auditoría del Contrato (Superficie de Exposición)

Dato / Campo Interno ¿Se expone en WSDL? Transformación / Política Justificación Técnica de Seguridad
concepts.id, concepts.name, concepts.definition SÍ Directo en ConceptoPendienteType Necesarios para que el clasificador lea la definición y asigne el modelo Cloud correcto.
books.isbn, books.title, books.year SÍ Directo Contexto bibliográfico indispensable para la clasificación temática.
books.price, books.stock, books.format NO Ocultado deliberadamente Datos comerciales y de inventario innecesarios para la tarea de clasificación.
users.* (Password hash, roles) NO Aislado completamente Información crítica de seguridad; el módulo SOAP gestiona sus propios clasificadores.
clasificaciones_cloud.ip_origen, cliente_id SÓLO EN AUDITORÍA Se recibe/captura pero no se devuelve al cliente Evita divulgar detalles de red interna a clientes de escritorio.
06

Operaciones Implementadas

El servicio implementa 4 operaciones bien delimitadas:

  • ObtenerConceptosPendientes: Retorna la lista de conceptos del catálogo pendientes por clasificar por un usuario dado, enriquecidos con título del libro y categoría.
  • RegistrarClasificacion: Valida identidad, modelo de servicio (IaaS | PaaS | SaaS | FaaS), verifica unicidad y persiste la clasificación retornando ID de transacción.
  • ObtenerProgresoUsuario: Calcula en tiempo real el conteo de conceptos clasificados, conceptos pendientes y porcentaje de avance del clasificador.
  • ObtenerEstadisticasPorModelo (Tarea 1): Operación administrativa sensible protegida por WS-Security que entrega el desglose métrico global del catálogo.

08

Seguridad y WS-Security (Tarea 1)

La operación ObtenerEstadisticasPorModelo expone métricas estratégicas agregadas del catálogo, por lo que se encuentra resguardada mediante WS-Security (UsernameToken) en el encabezado SOAP:

ENCABEZADO SOAP CON WS-SECURITY USERNAME TOKEN
<soapenv:Header>
    <wsse:Security xmlns:wsse="http://docs.oasis-open.org/wss/2004/01/oasis-200401-wss-wssecurity-secext-1.0.xsd">
        <wsse:UsernameToken>
            <wsse:Username>admin_clasificador</wsse:Username>
            <wsse:Password>CloudSecure2026!</wsse:Password>
        </wsse:UsernameToken>
    </wsse:Security>
</soapenv:Header>

Si la solicitud omite el encabezado o las credenciales no concuerdan, el servidor rechaza la petición con un SOAP Fault con código ERR_WS_SECURITY_UNAUTHORIZED y estado HTTP 401 Unauthorized sin acceder a la base de datos.

Aplicaciones de Escritorio como Clientes SOAP

Se desarrolló una aplicación de escritorio interactiva en Python (Tkinter) ubicada en client/desktop_classifier.py con tema oscuro moderno:

  • Captura de Identidad: Formulario para registrar nombre, apellidos y email del clasificador.
  • Catálogo Dinámico: Tabla Treeview que carga conceptos pendientes vía SOAP y muestra la definición completa del libro seleccionado.
  • Acción Transaccional: Selector de modelo (IaaS, PaaS, SaaS, FaaS) y botón de envío SOAP POST.
  • Manejo de SOAP Faults (Tarea 2): La GUI intercepta los códigos de falla (como 409 duplicado) y presenta alertas informativas claras sin exponer stack traces ni internals de PostgreSQL.
  • Modal WS-Security: Ventana protegida para autenticarse y consultar el panel de estadísticas globales.

Interoperabilidad con un Segundo Lenguaje (Tarea 4)

Se implementó un cliente desacoplado utilizando la biblioteca estándar Zeep (tests/client_zeep_interop.py). El cliente lee el archivo library-classifier.wsdl, compila los tipos XSD en tiempo de ejecución y genera los proxies de servicio automáticamente.

Resultado de Interoperabilidad: El WSDL sirvió como contrato estricto de integración. Un cliente desarrollado en Java (wsimport), .NET (dotnet-svcutil) o Python (zeep) puede consumir el servicio sin conocer que el backend está construido en Flask o que utiliza PostgreSQL.

Decisiones de Ingeniería y Trade-offs

Necesidad: Construcción y Procesamiento SOAP → Decisión: Parsing manual con xml.etree → Justificación: Control estricto del sobre → Ventajas: Sin dependencias pesadas → Limitaciones: Requiere construir XML explícitamente

Al implementar el parser manual, se evita la sobrecarga y "caja negra" de frameworks como Spyne, permitiendo un manejo exacto de los códigos HTTP y namespaces.

Necesidad: Proteger datos del monolito → Decisión: Tablas independientes y roles SQL → Justificación: Principio de mínimo privilegio → Ventajas: Cero riesgo de corrupción → Limitaciones: Requiere sincronización por claves foráneas

Las tablas clasificadores y clasificaciones_cloud no tocan la tabla users del monolito, preservando la integridad del negocio original.

Necesidad: Contrato estricto e interoperable → Decisión: Publicar WSDL en /soap?wsdl → Justificación: Estandarización de interfaz → Ventajas: Clientes autogenerables → Limitaciones: Menor flexibilidad ante cambios dinámicos

El contrato WSDL define formalmente los tipos XSD para que clientes en cualquier lenguaje (Java, .NET, Python) se integren sin ambigüedades.

Problemas Encontrados y Soluciones Técnicas

  • 1. Codificación en Consola Windows: En entornos con codepage CP1252, ciertos caracteres generaban UnicodeEncodeError. Solución: Se reconfiguró la salida estándar a UTF-8 y se utilizaron indicadores limpios tipo [OK] y [PASSED].
  • 2. Control de Concurrencia y Unicidad: Evitar condiciones de carrera al clasificar dos veces el mismo concepto. Solución: Se colocó la restricción UNIQUE (clasificador_id, concepto_id) en base de datos y se interceptó a nivel de capa de persistencia para mapearla a un SOAP Fault 409.
  • 3. Namespace Parsing: Los prefijos de namespace en XML a veces provocaban lecturas nulas en los hijos. Solución: Se creó la función auxiliar get_child_text() en soap/envelope.py que extrae el contenido local-name de forma robusta.

Conclusiones Personales y Preguntas de Reflexión

Respuestas a las Preguntas de Reflexión Técnica (PDF Pág. 9):

  1. ¿Qué pasaría si agregas un campo obligatorio a RegistrarClasificacion sin actualizar a los clientes? El validador XML o el parser del servidor rechazará la petición con un SOAP Fault (soapenv:Client), ya que el contrato WSDL/XSD impone una validación formal que rompe la compatibilidad hacia atrás si los clientes no envían el campo.
  2. ¿Qué información del WSDL podría ser útil para un atacante y qué no debería exponerse? El WSDL puede revelar la arquitectura interna, nombres de tablas/columnas, endpoints internos y versiones. No deben exponerse estructuras de base de datos completas, contraseñas, ni rutas físicas del servidor.
  3. ¿Por qué el tipado XSD aporta certeza al contrato? Porque define de forma no ambigua los tipos de datos (enteros, cadenas, fechas, enumeraciones permitidas), permitiendo validar los mensajes antes de que ingresen a la lógica de negocio.
  4. ¿Qué partes del Envelope fueron boilerplate y cuáles dependieron de la operación? Boilerplate: <soapenv:Envelope>, <soapenv:Header>, <soapenv:Body> y declaraciones de namespaces (70% del mensaje). Dependientes: los elementos hijos dentro del cuerpo (datos específicos de la operación).
  5. ¿Cuándo justificarías el overhead de XML frente a un formato más ligero? En entornos empresariales de banca, telecomunicaciones, gobierno o servicios legacy donde la rigidez del contrato (WSDL), la seguridad a nivel de mensaje (WS-Security/WS-Signature) y el no-repudio sean requisitos mandatorios más prioritarios que el ancho de banda.
  6. ¿Por qué un SOAP Fault es parte del contrato y no sólo un error HTTP? Porque SOAP Fault está estandarizado en el protocolo SOAP y permite transportar información estructurada del error (código de falla, subcódigo, detalle de negocio) independientemente del medio de transporte utilizado (HTTP, SMTP, JMS).
  7. ¿Cómo debe reaccionar una GUI ante un Fault de cliente frente a un Fault de servidor? Ante un Fault de cliente (400/409): mostrar una alerta interactiva clara al usuario indicando qué dato corregir (ej. "Clasificación duplicada"). Ante un Fault de servidor (500): mostrar un mensaje general de servicio no disponible y sugerir intentar más tarde, registrando el error en el log local.
  8. ¿Qué riesgo existe porque el módulo SOAP y el monolito compartan la misma base de datos? Riesgo de contención en bloqueos de tablas, acoplamiento al esquema y posible degradación de rendimiento por consultas cruzadas no indexadas.
  9. ¿Qué ocurriría si el monolito renombra books.isbn? ¿Cómo reducirías ese acoplamiento? El módulo SOAP fallaría al consultar esa columna. Para reducir el acoplamiento se deben utilizar vistas desacopladas (CREATE VIEW) o una capa de API intermedia en lugar de acceso directo por SQL.
  10. ¿Dónde debe aplicarse autenticación y qué problema resuelve WS-Security? Debe aplicarse en el encabezado del mensaje SOAP. WS-Security resuelve el problema de seguridad de extremo a extremo a nivel de mensaje (Message-Level Security), permitiendo que el mensaje viaje seguro a través de múltiples intermediarios y proxies sin depender exclusivamente de HTTPS punto a punto.
  11. ¿Es suficiente confiar en el correo enviado por el cliente para identificar al usuario? No es suficiente en entornos productivos críticos, ya que un cliente malicioso puede suplantar la identidad simplemente enviando otro correo. Se requiere un mecanismo de autenticación criptográfica como tokens firmados o UsernameToken con credenciales.
  12. ¿En qué escenarios empresariales seguirías eligiendo SOAP en 2026? En integraciones con sistemas bancarios centrales (Core Banking), plataformas gubernamentales (SAT, Facturación electrónica CFDI/PACs), aduanas y sistemas ERP heredados (SAP) que exigen contratos formales inmutables y estándares WS-* certificados.
